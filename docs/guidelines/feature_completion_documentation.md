# 기능 개발 완료 후 문서화 가이드라인

작성일: 2026-05-24

## 1. 목적

기능 개발이 끝난 뒤 구현 내용, 검증 결과, 남은 리스크가 코드와 함께 추적되도록 문서화 작업을 표준화한다.

이 가이드는 Runner.io 프로젝트에서 새로운 기능을 추가하거나 기존 기능을 크게 수정한 뒤 반드시 확인할 문서화 기준이다.

## 2. 완료 후 문서화 원칙

- 구현 완료 기능과 향후 확장 기능을 분리해서 쓴다.
- 실제 코드에 존재하는 파일, 서비스, 화면, DB 구조만 구현 완료로 기록한다.
- 테스트를 실행했다면 명령과 결과를 함께 남긴다.
- 실행하지 못한 테스트는 숨기지 않고 이유와 남은 확인 방법을 적는다.
- 사용자에게 보이는 변화와 내부 구조 변화를 모두 기록한다.
- 기존 문서와 README가 오래된 상태로 남지 않도록 관련 문서 목록을 함께 갱신한다.

## 3. 기능 완료 시 필수 문서화 작업

### 3.1 기능 변경 기록 문서 작성

새 기능 또는 큰 기능 변경은 `docs/feature_update_기능명.md` 형식으로 기록한다.

예시:

```text
docs/feature_update_achievements.md
docs/features/running_analysis/feature_update.md
```

문서에는 다음 항목을 포함한다.

````markdown
# 기능명 변경 기록

작성일: YYYY-MM-DD

## 1. 개요
- 왜 이 기능을 추가했는지
- 사용자에게 어떤 가치가 있는지
- MVP 범위와 제외 범위

## 2. 사용자 화면 변경
- 추가/수정된 화면
- 진입 경로
- 주요 UI 상태

## 3. 추가/수정 파일
| 파일 | 변경 내용 |
|---|---|

## 4. 데이터 흐름
```text
화면
-> 서비스
-> API/DB 또는 클라이언트 계산
-> UI 반영
```

## 5. 주요 계산/비즈니스 규칙
- 기준값
- 단위
- 예외 처리
- 경계값

## 6. 검증 결과
```bash
실행한 명령
```

결과:
- 통과/실패 여부
- 실패 후 수정 내용

## 7. 남은 확인 사항
- 실기기 확인
- 운영 데이터 확인
- 향후 확장
````

### 3.2 테스트 문서 갱신

기능 테스트가 추가되면 `docs/test_plan_and_results.md`를 갱신한다.

최소 갱신 항목:

- 새 테스트 파일명
- 검증 대상
- 실행 명령
- 실행 결과
- 수동 테스트가 필요한 경우 시나리오
- 남은 리스크

기록 형식:

````markdown
### 기능명 테스트

대상 파일:
- `test/example_service_test.dart`
- `test/example_page_test.dart`

검증 내용:
- 조건 계산
- 빈 상태
- 성공 상태
- 예외 상태
- 회귀 영향

실행 결과:

```bash
flutter test test/example_service_test.dart test/example_page_test.dart
flutter test
```

상태: 성공
````

### 3.3 프로젝트 구조 문서 갱신

새 파일, 새 화면, 새 서비스, 새 Edge Function, 새 DB 테이블이 생기면 `docs/PROJECT_STRUCTURE.md`를 갱신한다.

갱신 기준:

| 변경 유형 | 갱신 위치 |
|---|---|
| 새 화면 추가 | `lib/main` 표 |
| 새 서비스 추가 | `lib/services` 표 |
| 새 테스트 범위 추가 | 테스트 설명 |
| 새 Edge Function 추가 | Edge Functions 표 |
| 새 DB 테이블/RPC 추가 | 백엔드 구조 |
| 주요 데이터 흐름 변경 | 데이터 흐름 다이어그램 |

### 3.4 docs README 갱신

새 문서를 만들었으면 `docs/README.md`의 문서 목록과 읽기 순서를 갱신한다.

갱신 기준:

- 새 `feature_update_*.md` 문서 추가
- 새 에러 리포트 추가
- 새 가이드 문서 추가
- 문서 읽기 순서가 바뀐 경우 반영

### 3.5 루트 README 갱신 판단

사용자에게 보이는 기능, 실행 방법, 주요 기능 목록, 테스트 명령이 바뀌면 루트 `README.md`를 갱신한다.

갱신이 필요한 경우:

- 주요 기능 목록에 들어갈 만한 사용자 기능 추가
- 앱 화면 흐름 변경
- 설치/실행/테스트 명령 변경
- DB/API 구조 변경
- 구현 완료/부분 구현/향후 계획 구분 변경

갱신이 필요하지 않은 경우:

- 내부 리팩터링만 수행
- UI 문구만 소폭 수정
- 테스트만 보강하고 사용자 기능 변화 없음

## 4. 기능 완료 체크리스트

기능 완료 후 아래 순서로 점검한다.

| 단계 | 항목 | 완료 기준 |
|---|---|---|
| 1 | 변경 파일 확인 | `git status --short`로 범위 확인 |
| 2 | 구현 요약 정리 | 사용자 기능과 내부 변경 분리 |
| 3 | 테스트 실행 | 최소 관련 테스트와 `flutter analyze` 실행 |
| 4 | 테스트 결과 기록 | 명령/결과/실패 수정 사항 기록 |
| 5 | 기능 변경 문서 작성 | `docs/feature_update_기능명.md` 작성 |
| 6 | 테스트 문서 갱신 | `docs/test_plan_and_results.md` 갱신 |
| 7 | 구조 문서 갱신 | 새 화면/서비스/API/DB가 있으면 반영 |
| 8 | README 갱신 판단 | 사용자 기능 목록 변화가 있으면 반영 |
| 9 | 남은 리스크 기록 | 실기기/운영 데이터/수동 검증 항목 명시 |

## 5. 테스트 결과 기록 양식

기능 단위 테스트 결과는 아래 표를 사용한다.

| 테스트 ID | 테스트 항목 | 입력/상태 | 기대 결과 | 실제 결과 | 성공 여부 | 비고 |
|---|---|---|---|---|---|---|
| FEAT-U-001 | 단위 계산 | 기본 데이터 | 조건 통과 |  |  |  |
| FEAT-W-001 | 화면 표시 | 빈 데이터 | 빈 상태 표시 |  |  |  |
| FEAT-I-001 | 통합 흐름 | 저장 후 재조회 | UI 갱신 |  |  |  |
| FEAT-R-001 | 회귀 테스트 | 기존 주요 화면 | 정상 표시 |  |  |  |

## 6. 완료 보고 형식

작업 완료 후 사용자에게는 아래 순서로 짧게 보고한다.

```markdown
구현 완료했습니다.

변경:
- 파일/기능 요약

검증:
- `flutter analyze` 통과
- `flutter test ...` 통과

남은 확인:
- 실기기 확인 필요 여부
- 운영 데이터 확인 필요 여부
```

## 7. 배지/업적 기능 적용 예시

배지/업적 시스템처럼 하나의 기능 개발이 끝난 경우에는 다음 문서화가 필요하다.

필수:

- `docs/feature_update_achievements.md` 작성
- `docs/test_plan_and_results.md`에 배지 계산/UI 테스트 결과 추가
- `docs/PROJECT_STRUCTURE.md`에 `achievement_page.dart`, `achievement_service.dart` 추가
- `docs/README.md` 문서 목록 갱신

선택:

- 루트 `README.md` 주요 기능 목록에 배지/업적 추가
- 수동 테스트 결과가 생기면 별도 섹션으로 추가

## 8. 주의 사항

- 문서는 코드보다 앞서가면 안 된다. 아직 구현되지 않은 기능은 향후 확장으로 표시한다.
- 자동 테스트가 통과해도 실기기 의존 기능은 별도 수동 확인 필요 여부를 남긴다.
- Supabase 원격 DB를 사용하는 E2E 테스트는 테스트 데이터가 남을 수 있으므로 전용 계정/프로젝트 사용 여부를 기록한다.
- 민감 정보, access token, service role key, 개인 계정 정보는 문서에 쓰지 않는다.
