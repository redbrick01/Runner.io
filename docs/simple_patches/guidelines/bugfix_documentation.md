# 오류 수정 완료 후 문서화 가이드라인

작성일: 2026-05-24

## 1. 목적

오류를 수정한 뒤 같은 문제가 반복되지 않도록 재현 조건, 원인, 수정 범위, 검증 결과, 남은 리스크를 표준 형식으로 기록한다.

이 가이드는 Runner.io 프로젝트에서 버그, 장애, 회귀, 실기기 이슈, API/DB 데이터 불일치, 빌드/배포 실패를 수정한 뒤 적용한다.

## 2. 문서화 원칙

- 증상과 원인을 구분해서 쓴다.
- 재현 가능한 절차를 먼저 남긴다.
- 확인한 원인 후보와 최종 원인을 분리한다.
- 수정한 파일과 수정 의도를 함께 기록한다.
- 자동 테스트와 수동 테스트를 구분한다.
- 검증하지 못한 항목은 남은 확인 사항으로 명시한다.
- 추측은 "가능성", 확인된 사실은 "확인 결과"로 표현한다.
- 민감 정보, access token, service role key, 개인 계정 정보는 문서에 쓰지 않는다.

## 3. 오류 수정 문서 위치

오류 수정 보고서는 기본적으로 `docs/bug_fixes/` 아래에 저장한다.

파일명 규칙:

```text
docs/bug_fixes/이슈명_issue_report.md
docs/bug_fixes/이슈명_error_report.md
```

예시:

```text
docs/bug_fixes/dashboard_resume_error_report.md
docs/bug_fixes/ios_locked_split_tts_issue_report.md
```

## 6. 테스트 기록 기준

오류 수정 후 테스트 기록은 "재현 방지"가 핵심이다.

필수 테스트:

- 오류 재현 케이스가 수정 후 사라졌는지 확인
- 같은 영역의 정상 케이스가 유지되는지 확인
- 경계값 또는 예외값에서 크래시가 없는지 확인
- 관련 화면이 여전히 렌더링되는지 확인

가능하면 추가할 테스트:

- 단위 테스트: 원인 로직을 직접 검증
- Widget 테스트: 화면 상태와 에러 표시 검증
- Integration/E2E 테스트: API/DB 반영 검증
- 실기기 테스트: 위치, 권한, 백그라운드, 오디오, 지도처럼 시뮬레이터가 대체하기 어려운 기능 검증

테스트 결과 표:

| 테스트 ID | 유형 | 재현 조건 | 기대 결과 | 실제 결과 | 성공 여부 | 비고 |
|---|---|---|---|---|---|---|
| BUG-U-001 | Unit | 오류 원인 입력 | 정상 계산 |  |  |  |
| BUG-W-001 | Widget | 오류 화면 상태 | 안내 표시/복구 |  |  |  |
| BUG-I-001 | Integration | API/DB 흐름 | 데이터 일치 |  |  |  |
| BUG-R-001 | Regression | 기존 정상 흐름 | 회귀 없음 |  |  |  |
| BUG-M-001 | Manual | 실기기 조건 | 정상 동작 |  |  |  |

## 7. 문서 갱신 범위

오류 수정 후에는 아래 문서 갱신 여부를 판단한다.

| 문서 | 갱신 기준 |
|---|---|
| `docs/bug_fixes/*.md` | 모든 주요 오류 수정은 새 리포트 작성 |
| `docs/simple_patches/test_plan_and_results.md` | 새 테스트가 추가되었거나 검증 범위가 넓어진 경우 |
| `docs/simple_patches/PROJECT_STRUCTURE.md` | 오류 수정 과정에서 구조, 데이터 흐름, 서비스 책임이 바뀐 경우 |
| `docs/README.md` | 새 오류 리포트를 만들었거나 문서 읽기 순서가 바뀐 경우 |
| 루트 `README.md` | 사용자 안내, 실행 방법, 제한 사항이 바뀐 경우 |
| `docs/simple_patches/PRE_GIT_CHECKLIST.md` | 공개 전 주의해야 할 민감 정보/생성 파일/검증 명령이 바뀐 경우 |

## 8. 완료 보고 형식

오류 수정 완료 후 사용자에게는 아래 순서로 보고한다.

```markdown
오류 수정 완료했습니다.

원인:
- 핵심 원인 요약

수정:
- 파일/기능 요약

검증:
- `flutter analyze ...` 통과
- `flutter test ...` 통과

남은 확인:
- 실기기 또는 운영 데이터 확인 필요 여부
```

## 9. 기존 오류 리포트 참고 기준

새 오류 리포트를 작성할 때는 다음 기존 문서를 참고한다.

- `docs/bug_fixes/dashboard_resume_error_report.md`
  - 앱 생명주기, 캐시, API 응답 방어, 회귀 테스트 기록 예시
- `docs/bug_fixes/ios_locked_split_tts_issue_report.md`
  - iOS 실기기, 백그라운드, 네이티브 MethodChannel, 수동 테스트 계획 예시

## 10. 주의 사항

- 오류 수정 문서는 책임 추궁용이 아니라 재현 방지용 기록이다.
- 원인을 확정하지 못했다면 "최종 원인 미확정"으로 표시하고 확인한 후보와 방어 조치를 남긴다.
- 자동 테스트가 통과해도 실기기 조건이 핵심인 이슈는 완료 기준을 별도로 둔다.
- 운영 DB 데이터 수정이 포함되면 어떤 데이터에 어떤 보정이 들어갔는지 별도 섹션으로 남긴다.
