# AI Similarity Live Voice Coaching Plan

## Product Goal

러닝 중 1km마다 기존 구간 페이스 알림을 유지하면서, 현재 러닝 구간과 과거의 유사한 러닝 구간을 벡터 비교해 짧은 AI 코칭 문장을 함께 음성으로 제공한다.

목표 경험은 다음과 같다.

```text
3킬로미터, 구간 페이스 5분 48초.
비슷한 기록에선 여기서 페이스가 흔들렸어요. 호흡만 일정하게 가져가세요.
```

이 기능은 기존 `AI Running Similarity Analysis`의 저장 후 리포트 기능을 실시간 러닝 중 피드백으로 확장한다. 사용자는 단순한 페이스 숫자뿐 아니라 "내 과거 패턴 기준으로 지금 무엇을 조절해야 하는지"를 바로 들을 수 있어야 한다.

## Current Baseline

현재 1km 페이스 알림은 다음 위치에서 처리된다.

- Flutter foreground: `lib/main/running_map_page.dart`의 `_announceSplitIfNeeded()`
- Flutter TTS adapter: `lib/services/run_native_adapter.dart`
- Android background/native: `android/app/src/main/kotlin/com/example/runner_flutter/RunLockScreenService.kt`
- iOS background/native: `ios/Runner/RunLiveActivityPlugin.swift`

현재 음성 문구는 다음 형식이다.

```text
N킬로미터, 구간 페이스 M분 SS초
```

이미 구현된 AI 유사도 분석 기반은 다음과 같다.

- `run_ai_features`: 저장된 러닝의 summary, embedding, numeric feature, geometry summary 저장
- `run_ai_reports`: 저장 후 AI 분석 리포트 저장
- `match_similar_runs`: vector, numeric, PostGIS score를 조합해 유사 러닝 검색
- `generate-run-ai-report`: 저장된 러닝 기준 AI 리포트 생성
- `backfill-run-embeddings`: 기존 러닝 embedding 생성
- Flutter `RunAiReportService`: 리포트 생성/조회 API 호출

기존 기능은 전체 러닝 단위 비교가 중심이다. 실시간 음성 코칭에는 전체 러닝보다 1km split 단위 비교가 더 적합하다.

## User Experience

### Default Voice Output

기본 원칙은 기존 페이스 알림을 먼저 지연 없이 재생하고, AI 코칭은 텍스트 생성과 TTS 재생 준비가 끝나면 이어서 재생하는 것이다. AI 응답이 매우 빠른 경우에도 MVP의 안전한 기본값은 분리 재생이다.

```text
N킬로미터, 구간 페이스 M분 SS초.
[AI 응답 성공 시] AI 코칭 한 문장.
```

예시:

```text
1킬로미터, 구간 페이스 5분 20초. 초반이 조금 빠릅니다. 호흡을 아껴가세요.
3킬로미터, 구간 페이스 5분 48초. 비슷한 기록에선 여기서 흔들렸어요. 리듬만 유지하세요.
5킬로미터, 구간 페이스 5분 42초. 이전 유사 기록보다 안정적이에요. 지금 페이스를 이어가세요.
```

### Fallback Voice Output

AI 호출이 실패하거나 허용 window 안에 실제 음성으로 재생하기 어렵다면 기존 알림만 유지한다. 이미 페이스 알림을 재생한 뒤 AI 응답이 너무 늦게 도착하면 해당 코칭은 버리고 다음 km 알림에서 다시 시도한다.

```text
N킬로미터, 구간 페이스 M분 SS초
```

러닝 중 음성 지연은 사용자 경험을 해치므로 AI 코칭은 부가 기능이어야 하며, 페이스 알림 자체를 막으면 안 된다.

### Settings MVP

초기 설정은 최소 범위로 둔다.

- AI 페이스 코치: 켜기/끄기
- 피드백 빈도: 매 1km

MVP의 설정 저장 위치는 로컬 설정으로 시작한다. `SharedPreferences` 또는 기존 로컬 설정 저장소에 저장하고, 여러 기기 간 동기화가 필요해지면 profile 서버 설정으로 확장한다.

MVP 이후 확장 후보:

- 매 1km / 2km마다 / 후반부만
- 부드럽게 / 엄격하게 / 기록 중심
- 목표 페이스 또는 목표 거리
- 음성 길이 짧게 / 자세히

## Data Model

### Segment Embedding Table

실시간 코칭 품질을 위해 전체 러닝 embedding과 별도로 split 구간 embedding을 저장한다.

후보 테이블:

```sql
create table public.run_segment_ai_features (
  id bigint generated by default as identity primary key,
  user_id uuid not null references public.profiles(user_id),
  run_id bigint not null references public.runs(id) on delete cascade,
  split_index integer not null,
  embedding vector(384),
  feature_json jsonb not null default '{}'::jsonb,
  summary_text text not null,
  split_pace_s_per_km double precision,
  avg_pace_until_split_s_per_km double precision,
  pace_delta_prev_s double precision,
  pace_delta_avg_s double precision,
  distance_m double precision,
  duration_s double precision,
  ascent_m double precision,
  next_split_pace_s_per_km double precision,
  next_pace_delta_s double precision,
  next_outcome text,
  embedding_model text not null default 'gte-small',
  embedding_status text not null default 'pending',
  embedded_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (run_id, split_index)
);
```

권장 인덱스:

- `(user_id, split_index)`
- `(user_id, created_at desc)`
- vector index on `embedding`
- optional btree indexes on `split_pace_s_per_km`, `pace_delta_prev_s`

보안 정책:

- 테이블에는 RLS를 활성화한다.
- 클라이언트 직접 쓰기는 허용하지 않는다.
- Edge Function은 service role로 embedding/backfill/search를 수행한다.
- 클라이언트 직접 조회가 필요해지는 경우에도 `user_id = auth.uid()` select policy만 허용한다.
- 원본 GPS 좌표는 이 테이블과 LLM prompt에 저장/전달하지 않고, 구간 요약 feature만 사용한다.

### Segment Feature Input

구간 embedding은 원시 GPS 좌표보다 러닝 의미를 담은 요약 문장을 사용한다.

예시 JSON:

```json
{
  "completed_km": 3,
  "phase": "middle",
  "split_pace_s_per_km": 348,
  "avg_pace_until_split_s_per_km": 341,
  "pace_delta_prev_s": 12,
  "pace_delta_avg_s": 7,
  "trend": "slightly_fading",
  "ascent_m": 3.2,
  "pause_count": 0,
  "goal_context": "none",
  "next_outcome": "next split slowed by 18 seconds"
}
```

예시 summary text:

```text
3km 지점의 중반 구간. 이번 1km 페이스는 5분48초이고 전체 평균보다 7초 느리다. 이전 구간보다 12초 느려졌으며 페이스가 약간 떨어지는 패턴이다. 상승은 낮고 일시정지는 없다.
```

## Similarity Search

실시간 코칭은 같은 사용자의 과거 구간만 검색한다.

초기 검색 조건:

- `user_id = auth.uid()`
- 저장된 run을 기준으로 재분석할 때는 현재 `run_id`를 제외한다.
- 라이브 러닝 중에는 아직 저장된 `run_id`가 없을 수 있으므로 현재 run 제외 조건을 적용하지 않는다.
- `split_index`는 현재 km 기준 `-1`에서 `+1` 범위 우선
- 유사 구간 top 3~5개 반환
- 같은 run에서 너무 많은 구간이 몰리면 run별 최대 1~2개로 제한

후보 RPC:

```text
match_similar_run_segments(
  p_user_id uuid,
  p_split_index integer,
  p_embedding vector(384),
  p_feature_json jsonb,
  p_exclude_run_id bigint default null,
  p_limit integer default 5
)
```

점수는 MVP에서 단순하게 시작한다.

```text
total_score =
  embedding_score * 0.60 +
  split_index_score * 0.20 +
  numeric_score * 0.20
```

MVP 이후에는 목표 페이스, 상승고도, 전체 러닝 거리 bucket, 시간대, 코스 geometry를 추가할 수 있다.

유사 구간의 이후 결과는 코칭 품질에 중요하다. MVP에서는 `run_splits` self join으로 `split_index + 1` 구간을 조회하거나, backfill 시 `next_split_pace_s_per_km`, `next_pace_delta_s`, `next_outcome`을 `run_segment_ai_features`에 저장한다. Edge Function은 이 값을 사용해 "과거에는 이후 유지/회복/하락했는지"를 요약한 뒤 LLM에 전달한다.

## Edge Function Design

### New Function

신규 Edge Function 후보:

```text
generate-live-run-coaching
```

요청 body:

```json
{
  "run_session_id": "client-session-id",
  "completed_km": 3,
  "elapsed_seconds": 1020,
  "distance_meters": 3000,
  "split_duration_seconds": 348,
  "split_pace_seconds": 348,
  "average_pace_seconds": 341,
  "previous_split_paces": [330, 336],
  "current_speed_kmh": 10.1,
  "ascent_this_split_m": 3.2,
  "pause_count": 0,
  "goal_pace_seconds": null,
  "recent_coaching_categories": ["pace_control"],
  "exclude_run_id": null
}
```

응답 body:

```json
{
  "status": "completed",
  "coaching_message": "비슷한 기록에선 여기서 흔들렸어요. 호흡만 일정하게 가져가세요.",
  "similar_segment_count": 4,
  "fallback_used": false
}
```

실패 또는 데이터 부족 응답:

```json
{
  "status": "insufficient_data",
  "coaching_message": "페이스가 조금 흔들려요. 다음 구간은 리듬만 일정하게 가져가세요.",
  "similar_segment_count": 0,
  "fallback_used": true
}
```

### Server Flow

```text
generate-live-run-coaching
-> auth 확인
-> 현재 segment snapshot 정규화
-> segment summary text 생성
-> embedding 생성
-> match_similar_run_segments RPC 호출
-> 유사 구간의 다음 split 결과와 패턴 요약
-> OpenAI LLM 호출
-> 60자 이하 한국어 코칭 문장 반환
```

라이브 러닝은 저장 전 상태이므로 `run_id`가 없을 수 있다. `exclude_run_id`는 nullable로 두고, 저장된 러닝 재분석이나 디버그 호출에서만 사용한다. `run_session_id`는 서버 저장 식별자가 아니라 요청 추적과 로그 상관관계용으로만 사용한다.

### Prompt Contract

LLM은 서버에서만 호출한다.

요구 조건:

- 한국어 음성 코칭 한 문장
- 20자 이상 60자 이하
- 행동 제안은 하나만
- 숫자는 최대 2개
- 의료 진단, 부상 확정, 과도한 압박 금지
- "과거 유사 기록"을 근거로 하되 장황하게 설명하지 않음
- 사용자가 달리는 중이므로 읽어도 바로 이해되는 표현 사용

예시 system/developer instruction 요약:

```text
너는 러닝 중인 사용자에게 이어폰으로 들릴 짧은 코칭을 제공한다. 현재 구간과 과거 유사 구간 패턴을 보고 한국어 한 문장만 작성한다. 60자 이하로 말하고, 행동 제안은 하나만 포함한다. 의료적 진단이나 무리한 독려는 금지한다.
```

## Flutter Integration

### Service Layer

신규 서비스 후보:

```text
lib/services/live_run_coaching_service.dart
```

역할:

- 현재 split snapshot DTO 생성/전송
- `generate-live-run-coaching` 호출
- timeout 처리
- 응답 parsing
- 실패 시 null 또는 fallback 문구 반환
- 최근 coaching category 또는 message hash를 메모리에 보관해 반복 문구를 줄이는 데 사용

### RunningMapPage Flow

`_announceSplitIfNeeded()`의 기본 흐름을 유지하고 AI 코칭을 optional 단계로 추가한다.

```text
1km 도달
-> completedKm, splitDuration, splitPaceText 계산
-> baseSpeech 생성
-> baseSpeech를 기존 TTS 경로로 즉시 재생
-> AI 코치 설정이 켜져 있으면 coaching 요청 시작
-> AI 텍스트 생성 timeout 안에 응답이 있으면 TTS 큐에 등록
-> 음성 재생 허용 window 안이면 coachingMessage를 후속 TTS로 재생
-> 실패하거나 늦으면 해당 km의 AI 코칭은 생략
```

주의:

- AI 요청은 페이스 알림을 지연시키지 않는다.
- 앱 foreground와 Flutter 코드가 살아 있는 background 경로에서는 같은 `LiveRunCoachingService`를 사용한다.
- Android/iOS 네이티브 service/plugin이 Flutter 없이 자체적으로 split을 감지하는 "native-only background"에서는 Edge Function 호출 책임이 애매하다. MVP는 이 경로에서 기존 페이스 TTS만 유지하고, native-only AI 코칭은 후속 단계로 둔다.
- `previous_split_paces`는 라이브 코칭용으로 별도 누적한다. 구현 후보는 `RunningMapPage`의 메모리 리스트 또는 `RunSessionEngine`에서 노출하는 split history이며, MVP에서는 화면 상태와 함께 초기화되는 메모리 리스트로 시작한다.

### Timing Window

실시간 코칭은 "텍스트 생성 제한"과 "실제 음성 재생 허용 시간"을 분리한다. 사용자가 체감하는 기준은 API 응답 시간이 아니라 실제 이어폰/스피커에서 코칭이 시작되는 시점이다.

- 페이스 알림: AI 요청과 무관하게 즉시 재생
- AI 텍스트 생성 timeout: MVP 기본 8000ms
- AI 음성 시작 허용 window: 1km 도달 후 최대 12000ms
- 텍스트가 8000ms 안에 도착해도 TTS 큐 상황상 음성 시작이 12000ms를 넘을 것 같으면 폐기
- 다음 km 페이스 알림과 겹칠 가능성이 있으면 AI 코칭을 폐기하고 다음 km에서 다시 시도
- 실제 기기 QA에서 응답 분포를 보고 텍스트 timeout은 6000ms~10000ms, 음성 시작 window는 10000ms~15000ms 사이로 조정
- 페이스 알림과 AI 코칭 TTS가 겹치지 않도록 단일 TTS 큐를 사용한다.

## Backfill Plan

기존 러닝의 `run_splits`를 바탕으로 `run_segment_ai_features`를 생성한다.

신규 또는 확장 함수 후보:

- 기존 `backfill-run-embeddings` 확장
- 또는 `backfill-run-segment-embeddings` 신규 추가

처리 단계:

1. `run_segment_ai_features`에 없는 `run_splits`를 batch로 조회한다.
2. split index, split pace, 이전 split 대비 변화, 누적 평균 pace, 상승량을 계산한다.
3. 같은 run의 다음 split을 조회해 `next_split_pace_s_per_km`, `next_pace_delta_s`, `next_outcome`을 계산한다.
4. summary text와 feature_json을 생성한다.
5. Supabase built-in `gte-small` embedding을 생성한다.
6. `run_segment_ai_features`에 upsert한다.
7. 실패 row는 `embedding_status='failed'`로 저장하고 재시도 가능하게 한다.

운영 안전장치:

- batch size는 20~50개로 시작한다.
- LLM은 백필에서 호출하지 않는다. embedding만 생성한다.
- 운영 DB 적용 전 테스트 프로젝트에서 검색 품질을 샘플 검증한다.

## Development Phases

### Phase 1. Contract And Product Rules

- 음성 문구 길이, 텍스트 timeout, 음성 시작 window, fallback 기준 확정
- Flutter foreground, Flutter-backed background, native-only background 적용 범위 확정
- 사용자 설정 MVP 범위 확정
- 현재 split snapshot DTO 확정

완료 기준:

- `generate-live-run-coaching` request/response contract가 확정된다.
- "페이스 알림 즉시 재생, AI 텍스트 생성과 음성 시작 window 초과 시 생략" 원칙이 문서와 코드 설계에 반영된다.

### Phase 2. Segment Feature Storage

- `run_segment_ai_features` migration 추가
- RLS와 service role 중심 접근 정책 추가
- split feature 생성 유틸 추가
- 기존 `run_splits` 기반 segment embedding backfill 구현
- 다음 split outcome 계산 추가
- 샘플 데이터에서 feature_json과 summary_text 검증

완료 기준:

- 기존 러닝 split이 segment embedding row로 저장된다.

### Phase 3. Similar Segment Search

- `match_similar_run_segments` RPC 추가
- 같은 사용자, nullable 현재 run 제외, km 인접 조건 적용
- vector/numeric 혼합 score 계산
- 유사 구간의 다음 split outcome 반환
- SQL 테스트 또는 원격 검증 쿼리 작성

완료 기준:

- 현재 segment와 비슷한 과거 segment 3~5개를 안정적으로 반환한다.

### Phase 4. Live Coaching Edge Function

- `generate-live-run-coaching` 구현
- 현재 segment embedding 생성
- 유사 segment 검색 결과 요약
- OpenAI LLM 호출 및 짧은 문장 parsing

## Risks And Decisions

| 항목 | 리스크 | 대응 |
|---|---|---|
| 음성 지연 | AI 생성과 TTS 준비 때문에 코칭이 너무 늦게 들릴 수 있음 | 페이스 알림 즉시 재생, 텍스트 timeout 8000ms, 음성 시작 window 12000ms, 다음 km와 겹치면 폐기 |
| 저장 전 세션 | 라이브 러닝 중에는 아직 `run_id`가 없을 수 있음 | `exclude_run_id` nullable, `run_session_id`는 로그/추적 용도로만 사용 |
| 다음 구간 패턴 | 유사 구간 이후 결과가 없으면 코칭 근거가 약해짐 | next split self join 또는 backfill 저장으로 outcome 제공 |
| 네이티브 백그라운드 | Flutter 없이 native service가 split을 감지하면 API 호출 경로가 애매함 | MVP는 Flutter-backed 경로 우선, native-only AI는 후속 설계 |
| 데이터 부족 | 신규 사용자는 유사 segment가 없음 | 규칙 기반 fallback 코칭 제공 |
| 반복 문구 | 매 km마다 비슷한 조언이 반복될 수 있음 | 최근 코칭 문구 hash 또는 category를 request에 포함 |
| 비용 | 매 km LLM 호출로 비용 증가 | 설정 OFF 가능, 짧은 output, 빈도 옵션, fallback 활용 |
| 개인정보 | 러닝 위치와 건강 관련 데이터가 AI에 전달될 수 있음 | 원본 좌표 제외, 요약 feature만 전달, 서버 호출만 허용 |
| 안전 표현 | 무리한 독려나 의료적 표현 가능성 | prompt 금지 규칙, fallback 문구 whitelist |

## Recommended First Implementation Batch

첫 번째 batch는 사용자에게 바로 들리는 TTS 변경까지 욕심내지 않고, segment feature 기반을 먼저 만든다.

1. `run_segment_ai_features` migration 작성
2. RLS와 service role 중심 접근 정책 작성
3. `run_splits` -> segment summary/feature/next outcome 추출 유틸 작성
4. segment embedding backfill 구현
5. `match_similar_run_segments` RPC 구현
6. 샘플 payload로 유사 segment 검색 품질 검증

두 번째 batch에서 `generate-live-run-coaching`과 Flutter TTS 연결을 진행한다. 이때 페이스 알림은 즉시 재생하고 AI 코칭은 텍스트 생성과 TTS 큐 상태가 허용 window 안에 들어올 때만 후속 음성으로 붙이는 구조를 기본으로 한다. 이렇게 나누면 기존 페이스 알림 안정성을 유지하면서 벡터 검색 품질을 먼저 확인할 수 있다.
