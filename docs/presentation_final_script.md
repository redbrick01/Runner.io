# Runner.io 최종 발표 대본

## 1. 오프닝

안녕하세요. 저희는 Flutter 기반 영토 점령 게임화 러닝 앱, Runner.io 프로젝트를 구현했습니다.

이 프로젝트의 핵심은 사용자가 달린 기록을 단순히 거리와 시간으로 저장하는 데서 끝내지 않고, 그 기록이 앱 안에서 여러 기능으로 확장되도록 만든 것입니다.

발표에서는 먼저 왜 이런 구조를 만들었는지 설명하고, 이후 실제 구현한 화면 흐름, 데이터 처리 구조, 핵심 로직, AI 분석, 개발 과정과 보완점을 순서대로 설명드리겠습니다.

## 2. Background

먼저 프로젝트의 배경입니다.

기존 러닝 앱은 보통 거리, 시간, 페이스처럼 러닝의 기본 지표를 측정하고 기록하는 데 집중합니다. 저희도 이 기본 기록이 러닝 앱의 출발점이라고 보았습니다.

다만 이번 프로젝트에서는 여기서 한 단계 더 나아가, GPS 경로 데이터를 포인트, 랭킹, 영토 geometry, AI 리포트로 확장하는 구조를 구현해보고자 했습니다.

즉, 단순 기록 저장이 아니라 기록 데이터가 이후 여러 기능의 기반이 되는 구조를 만드는 것이 프로젝트의 출발점이었습니다.

## 3. Goals

다음은 프로젝트 목표입니다.

초기 아이디어에는 사용자가 달린 경로를 영토처럼 점령하는 게임성 요소가 있었습니다. 하지만 최종 구현에서는 단순 게임 기능에 머무르지 않고, 기록과 분석 중심의 러닝 앱으로 확장하는 것을 목표로 했습니다.

그래서 목표를 세 가지로 정리했습니다. 첫째, GPS를 기반으로 러닝 세션을 기록하는 것, 둘째, 그 기록을 지도와 영토, 포인트와 랭킹으로 확장하는 것, 셋째, AI 분석을 통해 사용자가 자신의 기록을 더 쉽게 이해하도록 돕는 것입니다.

## 4. Final Scope

최종 구현 범위는 현재 코드에 포함된 기능을 기준으로 정리했습니다.

먼저 회원가입, 로그인, 세션 체크, 프로필 수정 같은 인증과 프로필 기능을 구현했습니다. 그리고 러닝 시작, 일시정지, 재개, 종료, GPS 필터링, split 계산 같은 러닝 세션 기능을 구현했습니다.

지도와 영토 영역에서는 경로 폴리라인, 영토 폴리곤, PostGIS 기반 병합과 면적 계산을 다루었습니다. 결과와 분석 영역에서는 결과 리포트, 주간/월간/전체 통계, 최근 7일 그래프를 구성했습니다.

추가로 포인트 이력, 기간별 랭킹, 내 주변 순위 같은 게임화 기능, Android foreground service와 iOS Live Activity 같은 네이티브 연동, AI 러닝 리포트와 RAG 확장 설계까지 연결했습니다.

이후부터는 이 범위를 실제 사용 화면 흐름과 내부 처리 구조로 나누어 설명드리겠습니다.

## 5. User Guide

다음은 화면별 기능과 데이터 흐름입니다.

이 부분에서는 사용자가 어떤 화면에서 어떤 조작을 하고, 앱 내부에서는 어떤 데이터가 처리되며, 그 결과가 화면에 어떻게 표시되는지 순서대로 설명드리겠습니다.

첫 번째 기능은 회원가입과 로그인입니다.

이 앱은 이메일과 비밀번호 기반 인증을 사용하고, 앱 시작 시 기존 세션이 있는지 확인합니다. 세션이 없으면 로그인 화면으로 이동하고, 세션이 있으면 메인 지도 화면으로 이동합니다.

중요한 점은 인증이 완료된 뒤 모든 러닝 기록, 포인트, 랭킹, 영토 데이터가 사용자 ID를 기준으로 저장되고 조회된다는 것입니다. 그래서 인증은 이후 모든 기능의 기준이 됩니다.

두 번째 기능은 러닝 지도입니다.

지도 화면에서는 현재 위치, 달린 경로, 영토 폴리곤, 사용자 요약 정보를 확인할 수 있습니다. 사용자는 이 화면을 통해 현재 위치와 자신의 활동 영역을 확인하고 러닝을 시작합니다.

이 화면은 단순히 지도를 보여주는 화면이 아니라, 사용자가 달린 경로가 이후 영토 데이터로 변환되는 출발점입니다.

세 번째 기능은 러닝 세션 제어입니다.

사용자는 러닝을 시작하고, 중간에 일시정지하거나 재개할 수 있으며, 마지막에 종료할 수 있습니다. 앱 내부에서는 위치 샘플을 계속 받아서 거리, 속도, 페이스, 상승고도, split 데이터를 계산합니다.

여기서 중요한 점은 GPS 값이 항상 정확하지 않다는 것입니다. 그래서 비정상적인 위치 이동을 필터링하고, 일시정지 시간을 제외하며, 재개 후 거리 왜곡을 줄이는 처리를 함께 구현했습니다.

네 번째 기능은 러닝 결과 리포트입니다.

러닝이 종료되면 저장된 기록을 바탕으로 결과 화면이 구성됩니다. 이 화면에서는 거리, 시간, 평균 페이스 같은 기본 지표뿐 아니라 포인트, 칼로리, 상승고도, 점령 면적, 지도 경로, split 목록을 함께 보여줍니다.

즉, 러닝 중 수집하고 계산한 데이터가 사용자가 확인할 수 있는 결과 화면으로 정리되는 단계입니다.

다섯 번째 기능은 AI 러닝 분석입니다.

사용자가 AI 분석을 실행하면, 앱은 현재 러닝과 유사한 과거 기록을 먼저 검색합니다. 그리고 그 검색 결과를 AI 리포트 생성의 근거 데이터로 사용합니다.

생성된 리포트는 현재 기록에 대한 요약, 과거 기록과의 비교, 개선점, 다음 목표, 코칭 문구 형태로 표시됩니다.

이 기능은 단순히 AI에게 문장을 생성하게 하는 것이 아니라, 사용자의 실제 러닝 기록을 기반으로 현재 기록을 해석하려는 구조입니다.

여섯 번째 기능은 분석 화면입니다.

분석 화면은 저장된 러닝 기록을 주간, 월간, 전체 기준으로 집계해서 보여줍니다. 사용자는 총 거리, 러닝 시간, 러닝 횟수, 평균 페이스 같은 통계와 그래프를 확인할 수 있습니다.

결과 화면이 한 번의 러닝을 보여준다면, 분석 화면은 여러 번의 러닝 기록을 모아서 사용자의 운동 흐름을 보여주는 역할을 합니다.

일곱 번째 기능은 러닝 기록 조회입니다.

이 화면은 서버에 저장된 러닝 목록을 불러오고, 사용자가 선택한 기간 필터에 맞게 요약 지표를 계산합니다. 사용자는 일, 주, 월, 년, 전체 기준으로 기록을 확인할 수 있습니다.

또 러닝 카드 하나를 선택하면 해당 기록의 상세 결과 화면으로 이동할 수 있습니다. 그래서 이 화면은 저장된 러닝 기록과 상세 결과 화면을 연결하는 역할을 합니다.

여덟 번째 기능은 포인트 내역입니다.

이 화면에서는 포인트가 언제, 어떤 이유로 발생했는지 확인할 수 있습니다. 포인트 증감, 이벤트 유형, 연결된 러닝 기록, 합계 같은 정보를 보여줍니다.

따라서 사용자는 단순히 현재 포인트만 보는 것이 아니라, 포인트가 어떤 기록과 연결되어 발생했는지도 확인할 수 있습니다.

아홉 번째 기능은 포인트와 랭킹입니다.

이 화면은 일별 포인트 집계를 바탕으로 기간별 순위를 보여줍니다. 사용자는 일간, 주간, 월간, 연간, 전체 기준의 랭킹을 확인할 수 있고, 내 순위와 주변 순위도 볼 수 있습니다.

또 포인트가 발생한 러닝 결과로 이동할 수 있기 때문에, 랭킹 데이터와 실제 러닝 기록이 연결됩니다.

열 번째 기능은 점령 면적 상세입니다.

이 화면에서는 사용자의 현재 점령 면적, 오늘 증가한 면적, 주간 증가량을 확인할 수 있습니다. 또한 지도에서 영토 폴리곤과 관련 러닝 경로를 보고, 어떤 러닝으로 영토가 변화했는지도 타임라인으로 확인할 수 있습니다.

즉, GPS 경로가 PostGIS 기반 공간 데이터로 변환된 결과를 사용자가 직접 확인하는 화면입니다.

마지막 화면 기능은 마이페이지와 프로필입니다.

마이페이지에서는 사용자 요약 정보를 확인하고, 프로필 수정, 러닝 통계, 리포트, 점령 면적, 포인트 내역 같은 주요 화면으로 이동할 수 있습니다.

또 로그아웃도 이 화면에서 처리합니다. 프로필 정보는 러닝 기록과 포인트 계산에 필요한 사용자 기본 정보로 사용됩니다.

## 6. Technology Stack

다음은 사용 기술과 담당 역할입니다.

클라이언트 앱은 Flutter와 Dart로 구현했습니다. Flutter는 화면 구성, 상태 관리, 러닝 세션 처리, 서비스 계층을 담당합니다.

지도와 위치 기능에는 Google Maps와 Geolocator를 사용했습니다. 이를 통해 현재 위치, 러닝 경로, 영토 폴리곤을 표시하고 GPS 샘플을 수집했습니다.

백엔드는 Supabase를 사용했습니다. Supabase Auth는 이메일/비밀번호 인증과 세션 분기를 담당하고, Edge Functions는 러닝 저장, 기록 조회, 랭킹, 프로필, AI 분석 API를 담당합니다.

데이터베이스는 PostgreSQL과 PostGIS를 사용해 러닝 기록, 포인트, 랭킹, 영토 geometry, 공간 연산을 처리했습니다. Android와 iOS 네이티브 기능은 백그라운드 실행, 알림, Live Activity, Dynamic Island 표시를 위해 연동했습니다.

## 7. System Architecture

전체 시스템 구조는 크게 Flutter 앱, Supabase Edge Functions, PostgreSQL/PostGIS로 나눌 수 있습니다.

Flutter 앱은 사용자가 보는 화면, 지도, 러닝 상태, 실시간 GPS 처리와 같은 사용자 경험을 담당합니다.

Edge Functions는 러닝 저장, 기록 조회, 랭킹 조회, AI 분석 같은 서버 API 역할을 합니다.

PostgreSQL과 PostGIS는 실제 데이터 저장과 공간 연산을 담당합니다. 특히 영토 기능은 GPS 경로를 geometry로 변환하고, 병합이나 면적 계산 같은 처리가 필요하기 때문에 PostGIS를 사용했습니다.

정리하면 클라이언트는 실시간 UX를 담당하고, 서버는 저장과 후속 처리를 담당하며, DB와 PostGIS는 데이터 일관성과 공간 계산을 담당하는 구조입니다.

## 8. Runtime Data Flow

다음은 러닝 저장 후 처리되는 데이터 흐름입니다.

먼저 Geolocator를 통해 GPS 위치 샘플을 수집합니다. 이 샘플은 RunSessionEngine에서 필터링되고, 거리, 페이스, split 같은 값으로 계산됩니다.

러닝을 종료하면 create-run API를 통해 runs와 run_splits 데이터가 저장됩니다. 저장 이후에는 DB Trigger나 RPC를 통해 포인트, 랭킹, 영토, AI 분석용 feature 같은 파생 데이터가 갱신됩니다.

그 결과는 다시 결과 화면, 기록 화면, 포인트 화면, 랭킹 화면, 영토 화면에 반영됩니다.

즉, 클라이언트는 실시간 러닝 계산과 사용자 경험을 담당하고, 서버와 DB는 저장 이후의 파생 데이터를 일관되게 처리하는 구조입니다.

## 9. Core Logic

다음은 핵심 로직인 GPS 샘플 기반 러닝 기록 변환입니다.

GPS 위치 샘플은 그대로 사용하기 어렵습니다. 위치 정확도가 낮거나, 갑자기 비정상적으로 빠른 속도가 계산되는 경우가 있을 수 있기 때문입니다.

그래서 위치 정확도, 이동 거리, 파생 속도 기준으로 샘플을 필터링했습니다. 또한 러닝 시작 직후 불안정한 샘플을 처리하고, 일시정지 시간을 보정하며, split과 상승고도를 누적하는 로직을 구현했습니다.

러닝 상태도 idle, running, paused, resumed, stopped, cancelled처럼 나누어 관리했습니다. 이 과정을 통해 단순 GPS 좌표를 사용자가 볼 수 있는 러닝 기록으로 변환했습니다.

## 10. Data & API

다음은 주요 데이터와 API 구성입니다.

데이터는 크게 러닝 기록, 포인트와 랭킹, 영토, AI 분석 데이터로 나눌 수 있습니다.

러닝 기록에는 runs와 run_splits가 사용됩니다. 포인트와 랭킹에는 point_history와 user_point_daily 같은 집계 데이터가 사용됩니다. 영토에는 territories와 PostGIS geometry 데이터가 사용되고, AI 분석에는 run_ai_features와 run_ai_reports가 사용됩니다.

API도 이 역할에 맞게 나뉩니다. create-run은 러닝 저장을 담당하고, run-history는 기록 조회, point-history는 포인트 내역, profile-leaderboard는 랭킹, territory-geojson은 영토 지도 데이터, generate-run-ai-report와 run-ai-report는 AI 리포트 생성을 담당합니다.

## 11. Territory Processing

다음은 GPS 경로의 PostGIS 영토 변환입니다.

사용자가 달린 경로는 처음에는 GPS 좌표들의 연속입니다. 이 경로를 지도 위 선으로 표시하는 것에서 끝내지 않고, PostGIS geometry로 변환해 사용자별 영토 데이터로 저장했습니다.

이 과정에서는 경로를 정리하고, geometry로 변환하고, 면적을 계산하며, 기존 영토와 병합하거나 변화량을 계산하는 처리가 필요합니다.

이렇게 만들어진 영토 데이터는 GeoJSON 형태로 다시 앱에 전달되어 지도 위 폴리곤으로 표시됩니다.

## 12. Native Integration

다음은 백그라운드 실행과 잠금화면 표시입니다.

러닝 앱은 사용자가 달리는 동안 항상 화면을 켜두지 않습니다. 그래서 백그라운드에서도 기록이 유지되고, 잠금화면에서도 상태를 확인할 수 있어야 합니다.

Android에서는 foreground service를 사용해 백그라운드 위치 추적을 유지하고, notification action으로 일시정지, 재개, 종료를 처리했습니다.

iOS에서는 ActivityKit 기반 Live Activity를 사용해 잠금화면과 Dynamic Island에 러닝 상태를 표시했습니다.

이 부분은 Flutter 앱이지만 실제 모바일 환경에 필요한 기능을 Android와 iOS 네이티브 기능으로 보완한 사례입니다.

## 13. AI Running Analysis

다음은 AI 리포트 생성 흐름입니다.

AI 분석은 현재 러닝 하나만 보고 바로 문장을 생성하는 방식이 아닙니다. 먼저 현재 러닝과 유사한 과거 기록을 검색합니다.

유사도는 embedding score, numeric score, spatial score를 조합해 계산했습니다. 즉, 기록의 의미적 특징, 거리나 페이스 같은 수치 정보, 경로의 공간적 유사도를 함께 고려합니다.

이렇게 검색된 기록을 context로 전달하고, AI는 이를 바탕으로 현재 러닝의 요약, 개선점, 다음 목표, 코칭 문구를 생성합니다. 생성된 리포트는 저장된 뒤 결과 화면이나 분석 화면에서 확인할 수 있습니다.

## 14. RAG System Design

다음은 RAG 확장 설계입니다.

현재 구현 범위는 사용자 러닝 데이터 기반 retrieval입니다. 즉, 사용자의 과거 러닝 기록을 검색하고, 그 결과를 AI 리포트 생성의 근거로 사용하는 구조입니다.

다만 문서 기반 RAG와 자연어 기록 질의는 별도 확장 범위로 설계했습니다. 예를 들어 러닝 코칭 문서, 포인트 규칙, 영토 규칙 같은 문서를 chunk와 embedding으로 검색할 수 있습니다.

또 사용자가 "내 최근 기록을 보면 어떤 점을 개선해야 하나"처럼 자연어로 질문했을 때, 허용된 RPC를 통해 사용자 기록을 조회하고, 그 결과를 grounded context로 전달하는 구조로 확장할 수 있습니다.

개발은 Discovery, Feature Plan, Implementation, Verification, Report 순서로 진행했습니다.

## 17. Key Challenges

구현 중 처리한 주요 문제도 있었습니다.

첫 번째는 GPS 오차 필터링입니다. 부정확한 위치나 비정상적으로 빠른 이동이 기록에 반영되면 거리와 페이스가 왜곡되기 때문에, 위치 정확도와 이동 속도를 기준으로 필터링했습니다.

두 번째는 러닝 상태 보정입니다. 일시정지 시간을 제외하고, 재개 후 갑자기 먼 위치가 들어오는 경우를 별도 segment로 처리해 거리 왜곡을 줄였습니다.

세 번째는 영토 geometry 처리입니다. GPS 경로를 PostGIS geometry로 변환하고, 사용자 영토를 생성, 병합, 차감하는 서버 로직을 구성했습니다.

네 번째는 백그라운드 실행입니다. Flutter 앱 외부에서 Android foreground service와 iOS Live Activity를 연동해 실제 러닝 환경을 보조했습니다.

다섯 번째는 AI 분석 안정화입니다. 유사도 계산과 structured output schema 오류를 수정하고, 실제 기기에서 리포트 생성이 가능한지 검증했습니다.

마지막으로 데이터 정합성 문제도 처리했습니다. 포인트 집계가 누락되는 문제를 migration과 backfill로 수정하고 테스트로 확인했습니다.
