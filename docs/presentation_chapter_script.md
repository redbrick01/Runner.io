# Runner.io 발표 흐름 재구성

## 작성 기준

- 이 문서는 프레젠테이션 웹페이지의 실제 섹션 순서를 기준으로 재구성했다.
- 발표 흐름은 `배경 → 목표 → 구현 범위 → 화면별 기능 → 시스템 구조 → 핵심 처리 로직 → 개발 과정 → 결과와 보완` 순서다.
- 발표자는 각 장의 `핵심 메시지`만 보고도 흐름을 이어갈 수 있고, `발표 대본`은 그대로 읽거나 말투에 맞게 줄여서 사용할 수 있다.
- 대학교 프로젝트 발표이므로 기능 홍보보다 `문제 정의`, `구현한 범위`, `기술 적용 이유`, `검증과 한계`를 중심으로 설명한다.

## 1. 오프닝: Runner.io 소개

### 핵심 메시지

- 첫 문장은 "GPS 러닝 기록을 기반으로 여러 기능을 연결한 러닝 앱 구현 프로젝트"라고 잡는다.
- 이 프로젝트는 러닝 앱을 처음부터 상용 서비스처럼 소개하기보다, 졸업 프로젝트에서 어떤 기능과 구조를 구현했는지 보여주는 발표다.
- 핵심은 GPS 기록을 단순히 저장하는 데서 끝내지 않고, 지도 표시, 포인트/랭킹, 영토, AI 러닝 리포트, RAG 확장 설계까지 하나의 구조로 연결했다는 점이다.
- 도입부에서는 세부 기술을 바로 설명하지 말고, "사용자의 러닝 한 번이 앱 안에서 여러 데이터와 화면으로 확장된다"는 큰 그림을 먼저 말한다.

### 발표 대본

안녕하세요. 저희는 GPS 러닝 기록을 기반으로 지도 표시, 포인트와 랭킹, 영토 처리, AI 러닝 리포트 기능을 연결한 Runner.io 프로젝트를 구현했습니다.

이 프로젝트의 핵심은 사용자가 달린 기록을 단순히 거리와 시간으로 저장하는 데서 끝내지 않고, 그 기록이 앱 안에서 여러 기능으로 확장되도록 만든 것입니다.

발표에서는 먼저 왜 이런 구조를 만들었는지 설명하고, 이후 실제 구현한 화면 흐름, 데이터 처리 구조, 핵심 로직, AI 분석, 개발 과정과 보완점을 순서대로 설명드리겠습니다.

## 2. Background: 기존 러닝 앱의 기록 중심 구조

### 핵심 메시지

- 웹페이지의 첫 번째 본론은 "기존 러닝 앱은 거리, 시간, 페이스 측정 중심"이라는 문제의식에서 시작한다.
- 여기서 말해야 할 포인트는 기존 앱이 부족하다고 비판하는 것이 아니라, 이번 프로젝트가 기록 데이터를 더 넓게 활용해보려 했다는 점이다.
- 기본 러닝 데이터는 거리, 시간, 페이스이고, 이 데이터에 후속 처리 구조를 붙이면 포인트/랭킹, 공간 데이터, AI 리포트로 확장할 수 있다.
- 이 장은 뒤에 나올 모든 기능의 출발점이다. "기록 데이터가 있어야 뒤의 기능들이 가능하다"는 식으로 연결한다.

### 발표 대본

먼저 프로젝트의 배경입니다.

기존 러닝 앱은 보통 거리, 시간, 페이스처럼 러닝의 기본 지표를 측정하고 기록하는 데 집중합니다. 저희도 이 기본 기록이 러닝 앱의 출발점이라고 보았습니다.

다만 이번 프로젝트에서는 여기서 한 단계 더 나아가, GPS 경로 데이터를 포인트, 랭킹, 영토 geometry, AI 리포트로 확장하는 구조를 구현해보고자 했습니다.

즉, 단순 기록 저장이 아니라 기록 데이터가 이후 여러 기능의 기반이 되는 구조를 만드는 것이 프로젝트의 출발점이었습니다.

## 3. Goals: 게임성에서 러닝 앱 완성도로 확장

### 핵심 메시지

- 웹페이지의 두 번째 흐름은 "영토 점령 게임성"에서 "기록과 분석 중심의 러닝 앱"으로 확장하는 것이다.
- 발표에서는 게임성을 최종 목적처럼 말하지 말고, 러닝 기록을 더 잘 활용하기 위한 한 요소라고 설명한다.
- 목표는 크게 세 가지다. 첫째, GPS 기반 기록을 안정적으로 남긴다. 둘째, 지도/영토/포인트로 기록을 확장한다. 셋째, AI 분석으로 기록을 해석한다.
- 이 장에서는 "재미 요소 + 기록 분석 + 사용 편의"가 함께 들어간 러닝 앱 구현이 목표였다고 정리한다.

### 발표 대본

다음은 프로젝트 목표입니다.

초기 아이디어에는 사용자가 달린 경로를 영토처럼 점령하는 게임성 요소가 있었습니다. 하지만 최종 구현에서는 단순 게임 기능에 머무르지 않고, 기록과 분석 중심의 러닝 앱으로 확장하는 것을 목표로 했습니다.

그래서 목표를 세 가지로 정리했습니다. 첫째, GPS를 기반으로 러닝 세션을 기록하는 것, 둘째, 그 기록을 지도와 영토, 포인트와 랭킹으로 확장하는 것, 셋째, AI 분석을 통해 사용자가 자신의 기록을 더 쉽게 이해하도록 돕는 것입니다.

## 4. Final Scope: 최종 구현 범위

### 핵심 메시지

- 이 장은 발표의 범위를 명확히 정하는 역할이다.
- 구현 범위는 인증/프로필, 러닝 기록, 지도/영토, 결과/분석, 게임화, 네이티브 연동, AI 분석과 RAG 검색 설계로 나뉜다.
- 여기서는 모든 기능을 깊게 설명하지 말고, "이 범위를 실제 코드에 연결해 구현했고, 이후 장에서 화면과 구조로 나누어 설명한다"고 말한다.
- 발표자가 흐름을 잡을 때 이 장은 목차 역할을 한다.

### 발표 대본

최종 구현 범위는 현재 코드에 포함된 기능을 기준으로 정리했습니다.

먼저 회원가입, 로그인, 세션 체크, 프로필 수정 같은 인증과 프로필 기능을 구현했습니다. 그리고 러닝 시작, 일시정지, 재개, 종료, GPS 필터링, split 계산 같은 러닝 세션 기능을 구현했습니다.

지도와 영토 영역에서는 경로 폴리라인, 영토 폴리곤, PostGIS 기반 병합과 면적 계산을 다루었습니다. 결과와 분석 영역에서는 결과 리포트, 주간/월간/전체 통계, 최근 7일 그래프를 구성했습니다.

추가로 포인트 이력, 기간별 랭킹, 내 주변 순위 같은 게임화 기능, Android foreground service와 iOS Live Activity 같은 네이티브 연동, AI 러닝 리포트와 RAG 확장 설계까지 연결했습니다.

이후부터는 이 범위를 실제 사용 화면 흐름과 내부 처리 구조로 나누어 설명드리겠습니다.

## 5. User Guide: 화면별 기능과 데이터 흐름

### 핵심 메시지

- 실제 웹페이지는 구현 범위 다음에 화면별 기능 11개를 먼저 보여준다. 즉, 사용자가 앱을 어떻게 쓰는지 먼저 설명한 뒤 내부 구조로 들어가는 흐름이다.
- 이 챕터는 기술 설명보다 "사용자가 어떤 조작을 하고, 앱 내부에서는 어떤 데이터가 처리되며, 화면에는 어떤 결과가 보이는지"를 설명하는 부분이다.
- 11개 기능은 앱 사용 순서에 가깝다. 인증 → 지도 → 러닝 제어 → 결과 → AI 분석 → 통계 → 기록 → 포인트 내역 → 랭킹 → 영토 상세 → 마이페이지 순서로 이해하면 된다.
- 발표할 때는 각 기능을 길게 설명하지 말고, 사용자의 흐름이 끊기지 않게 연결한다.

### 5.1 Feature 01: 회원가입 / 로그인

#### 핵심 메시지

- 첫 화면 기능은 Supabase Auth 기반 이메일/비밀번호 인증이다.
- 앱 시작 시 세션을 확인해서 로그인 화면으로 갈지, 메인 지도 화면으로 갈지 분기한다.
- 인증 성공 후에는 모든 러닝 기록, 포인트, 랭킹, 영토 데이터가 사용자 ID 기준으로 연결된다.
- 이 기능은 단순 로그인 기능이 아니라, 이후 모든 데이터의 소유자를 확정하는 출발점이다.

#### 발표 대본

첫 번째 기능은 회원가입과 로그인입니다.

이 앱은 이메일과 비밀번호 기반 인증을 사용하고, 앱 시작 시 기존 세션이 있는지 확인합니다. 세션이 없으면 로그인 화면으로 이동하고, 세션이 있으면 메인 지도 화면으로 이동합니다.

중요한 점은 인증이 완료된 뒤 모든 러닝 기록, 포인트, 랭킹, 영토 데이터가 사용자 ID를 기준으로 저장되고 조회된다는 것입니다. 그래서 인증은 이후 모든 기능의 기준이 됩니다.

### 5.2 Feature 02: 러닝 지도

#### 핵심 메시지

- 메인 화면은 Google Map 위에 현재 위치, 경로, 영토 폴리곤, 사용자 요약 정보를 보여주는 화면이다.
- 사용자는 이 화면에서 자신의 위치와 기존 영토 상태를 확인하고 러닝을 시작한다.
- 이 화면의 핵심은 "지도에서 보는 정보"와 "이후 공간 데이터로 변환될 GPS 경로"를 연결하는 것이다.
- 발표에서는 메인 지도 화면을 앱의 진입점이자 GPS 기록이 공간 데이터로 이어지는 출발점으로 설명한다.

#### 발표 대본

두 번째 기능은 러닝 지도입니다.

지도 화면에서는 현재 위치, 달린 경로, 영토 폴리곤, 사용자 요약 정보를 확인할 수 있습니다. 사용자는 이 화면을 통해 현재 위치와 자신의 활동 영역을 확인하고 러닝을 시작합니다.

이 화면은 단순히 지도를 보여주는 화면이 아니라, 사용자가 달린 경로가 이후 영토 데이터로 변환되는 출발점입니다.

### 5.3 Feature 03: 러닝 세션 제어

#### 핵심 메시지

- 러닝 세션은 시작, 일시정지, 재개, 종료, 취소 상태를 가진다.
- 위치 샘플은 세션 엔진으로 전달되고, 엔진은 거리, 속도, 페이스, 상승고도, split 등을 계산한다.
- 일시정지 시간 제외, GPS 오차 제거, 재개 후 거리 보정처럼 실제 러닝 기록 품질을 위한 처리가 들어간다.
- 이 장은 "GPS를 받는 것"과 "믿을 수 있는 러닝 기록으로 계산하는 것"이 다르다는 점을 설명하는 핵심 구간이다.

#### 발표 대본

세 번째 기능은 러닝 세션 제어입니다.

사용자는 러닝을 시작하고, 중간에 일시정지하거나 재개할 수 있으며, 마지막에 종료할 수 있습니다. 앱 내부에서는 위치 샘플을 계속 받아서 거리, 속도, 페이스, 상승고도, split 데이터를 계산합니다.

여기서 중요한 점은 GPS 값이 항상 정확하지 않다는 것입니다. 그래서 비정상적인 위치 이동을 필터링하고, 일시정지 시간을 제외하며, 재개 후 거리 왜곡을 줄이는 처리를 함께 구현했습니다.

### 5.4 Feature 04: 러닝 결과 리포트

#### 핵심 메시지

- 러닝 종료 후 저장된 기록은 결과 리포트 화면에서 지도, 주요 지표, split, 포인트, 점령 면적으로 표시된다.
- 결과 화면은 create-run 저장 결과와 서버에서 계산된 파생 값을 사용한다.
- 사용자는 거리, 시간, 평균 페이스, 포인트, 칼로리, 상승고도, 점령 면적, 지도 경로, split 목록을 확인한다.
- 이 장은 "러닝 중 계산된 데이터가 사용자가 확인할 수 있는 결과 화면으로 정리된다"는 흐름을 보여준다.

#### 발표 대본

네 번째 기능은 러닝 결과 리포트입니다.

러닝이 종료되면 저장된 기록을 바탕으로 결과 화면이 구성됩니다. 이 화면에서는 거리, 시간, 평균 페이스 같은 기본 지표뿐 아니라 포인트, 칼로리, 상승고도, 점령 면적, 지도 경로, split 목록을 함께 보여줍니다.

즉, 러닝 중 수집하고 계산한 데이터가 사용자가 확인할 수 있는 결과 화면으로 정리되는 단계입니다.

### 5.5 Feature 05: AI 러닝 분석

#### 핵심 메시지

- 결과 화면에서 AI 분석을 실행하면 현재 러닝과 유사한 과거 기록을 검색한다.
- 검색 결과는 AI 리포트를 생성할 때 근거 데이터로 사용된다.
- 생성 결과는 요약, 비교, 개선점, 코칭 문구처럼 사용자가 이해할 수 있는 형태로 저장되고 표시된다.
- 이 기능은 단순 통계가 아니라 과거 기록 검색 결과를 바탕으로 현재 러닝을 해석하려는 시도다.

#### 발표 대본

다섯 번째 기능은 AI 러닝 분석입니다.

사용자가 AI 분석을 실행하면, 앱은 현재 러닝과 유사한 과거 기록을 먼저 검색합니다. 그리고 그 검색 결과를 AI 리포트 생성의 근거 데이터로 사용합니다.

생성된 리포트는 현재 기록에 대한 요약, 과거 기록과의 비교, 개선점, 다음 목표, 코칭 문구 형태로 표시됩니다.

이 기능은 단순히 AI에게 문장을 생성하게 하는 것이 아니라, 사용자의 실제 러닝 기록을 기반으로 현재 기록을 해석하려는 구조입니다.

### 5.6 Feature 06: 분석 화면

#### 핵심 메시지

- 분석 화면은 저장된 러닝 기록을 주간, 월간, 전체 기준으로 집계한다.
- 통계 카드와 그래프를 통해 총 거리, 시간, 횟수, 평균 페이스, 최근 AI 요약 등을 보여준다.
- 빈 기록 상태, 그래프 범위, 기간 필터 같은 화면 상태도 고려한다.
- 이 장에서는 "한 번의 결과"가 아니라 "누적 기록을 요약해 보여주는 화면"이라고 설명한다.

#### 발표 대본

여섯 번째 기능은 분석 화면입니다.

분석 화면은 저장된 러닝 기록을 주간, 월간, 전체 기준으로 집계해서 보여줍니다. 사용자는 총 거리, 러닝 시간, 러닝 횟수, 평균 페이스 같은 통계와 그래프를 확인할 수 있습니다.

결과 화면이 한 번의 러닝을 보여준다면, 분석 화면은 여러 번의 러닝 기록을 모아서 사용자의 운동 흐름을 보여주는 역할을 합니다.

### 5.7 Feature 07: 러닝 기록 조회

#### 핵심 메시지

- 러닝 기록 조회 화면은 저장된 러닝 목록을 불러오고, 기간 필터에 맞게 요약 지표를 계산한다.
- 사용자는 일/주/월/년/전체 필터를 선택하고, 총 거리, 총 포인트, 총 점령 면적 등을 확인한다.
- 러닝 카드를 선택하면 상세 결과 화면으로 이동한다.
- 이 기능은 저장된 raw 데이터를 다시 결과 화면과 연결하는 중간 화면이다.

#### 발표 대본

일곱 번째 기능은 러닝 기록 조회입니다.

이 화면은 서버에 저장된 러닝 목록을 불러오고, 사용자가 선택한 기간 필터에 맞게 요약 지표를 계산합니다. 사용자는 일, 주, 월, 년, 전체 기준으로 기록을 확인할 수 있습니다.

또 러닝 카드 하나를 선택하면 해당 기록의 상세 결과 화면으로 이동할 수 있습니다. 그래서 이 화면은 저장된 러닝 기록과 상세 결과 화면을 연결하는 역할을 합니다.

### 5.8 Feature 08: 포인트 내역

#### 핵심 메시지

- 사용자는 어떤 러닝이나 이벤트 때문에 포인트가 생겼는지 추적할 수 있다.
- 이 기능은 포인트를 단순 총합으로만 보여주지 않고, 발생 근거를 확인하게 해준다.

여덟 번째 기능은 포인트 내역입니다.

따라서 사용자는 단순히 현재 포인트만 보는 것이 아니라, 포인트가 어떤 기록과 연결되어 발생했는지도 확인할 수 있습니다.

이 화면은 일별 포인트 집계를 바탕으로 기간별 순위를 보여줍니다. 사용자는 일간, 주간, 월간, 연간, 전체 기준의 랭킹을 확인할 수 있고, 내 순위와 주변 순위도 볼 수 있습니다.

## 7. System Architecture: 역할을 나누는 구조

### 핵심 메시지

- 이 장은 Flutter 앱, Edge Function, PostGIS가 어떤 역할을 나누는지 보여준다.
- Flutter Client는 화면 상태와 실시간 러닝 세션을 처리한다.
- Supabase Backend는 인증, Edge Functions, DB 저장, RPC 호출을 담당한다.
- PostGIS는 runs, points, territories, AI features 같은 데이터를 저장하고 공간 계산을 수행한다.
- 발표에서는 "클라이언트는 실시간 UX, 서버는 저장과 파생 데이터, DB/PostGIS는 일관된 계산"이라는 역할 분담을 강조한다.

### 발표 대본

전체 시스템 구조는 크게 Flutter 앱, Supabase Edge Functions, PostgreSQL/PostGIS로 나눌 수 있습니다.

Flutter 앱은 사용자가 보는 화면, 지도, 러닝 상태, 실시간 GPS 처리와 같은 사용자 경험을 담당합니다.

Edge Functions는 러닝 저장, 기록 조회, 랭킹 조회, AI 분석 같은 서버 API 역할을 합니다.

PostgreSQL과 PostGIS는 실제 데이터 저장과 공간 연산을 담당합니다. 특히 영토 기능은 GPS 경로를 geometry로 변환하고, 병합이나 면적 계산 같은 처리가 필요하기 때문에 PostGIS를 사용했습니다.

정리하면 클라이언트는 실시간 UX를 담당하고, 서버는 저장과 후속 처리를 담당하며, DB와 PostGIS는 데이터 일관성과 공간 계산을 담당하는 구조입니다.

## 8. Runtime Data Flow: 러닝 저장 후 처리되는 데이터 흐름

### 핵심 메시지

- 이 장은 발표의 핵심 흐름이다. 사용자가 러닝을 끝낸 뒤 내부에서 어떤 순서로 데이터가 처리되는지 설명한다.
- GPS Stream → RunSessionEngine → create-run → DB Trigger/RPC → Result/History/Point/Ranking/Territory 순서로 말한다.
- 클라이언트는 실시간 계산과 UX를 담당하고, 저장 이후 포인트/영토/랭킹 같은 파생 처리는 서버와 DB가 일관되게 처리한다.
- 이 흐름을 이해하면 뒤의 Core Logic, Data & API, Territory, AI 챕터가 자연스럽게 이어진다.

### 발표 대본

다음은 러닝 저장 후 처리되는 데이터 흐름입니다.

먼저 Geolocator를 통해 GPS 위치 샘플을 수집합니다. 이 샘플은 RunSessionEngine에서 필터링되고, 거리, 페이스, split 같은 값으로 계산됩니다.

러닝을 종료하면 create-run API를 통해 runs와 run_splits 데이터가 저장됩니다. 저장 이후에는 DB Trigger나 RPC를 통해 포인트, 랭킹, 영토, AI 분석용 feature 같은 파생 데이터가 갱신됩니다.

그 결과는 다시 결과 화면, 기록 화면, 포인트 화면, 랭킹 화면, 영토 화면에 반영됩니다.

즉, 클라이언트는 실시간 러닝 계산과 사용자 경험을 담당하고, 서버와 DB는 저장 이후의 파생 데이터를 일관되게 처리하는 구조입니다.

## 9. Core Logic: GPS 샘플 기반 러닝 기록 변환

### 핵심 메시지

- 이 장은 GPS 위치 샘플을 신뢰할 수 있는 러닝 기록으로 바꾸는 핵심 로직을 설명한다.
- 상태 관리는 idle, running, paused, resumed, stopped, cancelled처럼 나뉜다.
- 샘플 처리 기준은 maximum accuracy filtering, minimum movement threshold, abnormal derived-speed filtering, warm-up sample handling, paused-time compensation, split/ascent accumulation이다.
- 발표에서는 "GPS는 오차가 있기 때문에 필터링과 상태 보정이 필요했다"고 말한다.

### 발표 대본

다음은 핵심 로직인 GPS 샘플 기반 러닝 기록 변환입니다.

GPS 위치 샘플은 그대로 사용하기 어렵습니다. 위치 정확도가 낮거나, 갑자기 비정상적으로 빠른 속도가 계산되는 경우가 있을 수 있기 때문입니다.

그래서 위치 정확도, 이동 거리, 파생 속도 기준으로 샘플을 필터링했습니다. 또한 러닝 시작 직후 불안정한 샘플을 처리하고, 일시정지 시간을 보정하며, split과 상승고도를 누적하는 로직을 구현했습니다.

러닝 상태도 idle, running, paused, resumed, stopped, cancelled처럼 나누어 관리했습니다. 이 과정을 통해 단순 GPS 좌표를 사용자가 볼 수 있는 러닝 기록으로 변환했습니다.

## 11. Territory Processing: GPS 경로의 PostGIS 영토 변환

### 핵심 메시지

- 이 장은 이 프로젝트의 공간 데이터 처리 파트다.
- GPS 경로는 단순 polyline에서 끝나는 것이 아니라, PostGIS geometry로 변환되어 사용자별 영토 데이터가 된다.
- 핵심 처리는 경로 정리, geometry 변환, 면적 계산, 기존 영토와의 병합/차감, GeoJSON 응답 구성이다.
- 발표에서는 "달린 경로를 지도 위 선으로만 보여주는 것이 아니라, 공간 데이터로 저장하고 다시 화면에 보여준다"고 설명한다.

### 발표 대본

다음은 GPS 경로의 PostGIS 영토 변환입니다.

사용자가 달린 경로는 처음에는 GPS 좌표들의 연속입니다. 이 경로를 지도 위 선으로 표시하는 것에서 끝내지 않고, PostGIS geometry로 변환해 사용자별 영토 데이터로 저장했습니다.

이 과정에서는 경로를 정리하고, geometry로 변환하고, 면적을 계산하며, 기존 영토와 병합하거나 변화량을 계산하는 처리가 필요합니다.

이렇게 만들어진 영토 데이터는 GeoJSON 형태로 다시 앱에 전달되어 지도 위 폴리곤으로 표시됩니다.

## 12. Native Integration: 백그라운드 실행과 잠금화면 표시

### 핵심 메시지

- 러닝 앱은 화면이 꺼지거나 백그라운드로 내려가도 기록이 유지되어야 한다.
- Android는 foreground service와 notification action을 사용해 pause/resume/stop을 처리한다.
- iOS는 ActivityKit 기반 Live Activity와 Dynamic Island 표시를 사용한다.
- 이 장에서는 Flutter만으로 어려운 모바일 OS 기능을 네이티브 연동으로 보완했다는 점을 강조한다.

### 발표 대본

다음은 백그라운드 실행과 잠금화면 표시입니다.

러닝 앱은 사용자가 달리는 동안 항상 화면을 켜두지 않습니다. 그래서 백그라운드에서도 기록이 유지되고, 잠금화면에서도 상태를 확인할 수 있어야 합니다.

Android에서는 foreground service를 사용해 백그라운드 위치 추적을 유지하고, notification action으로 일시정지, 재개, 종료를 처리했습니다.

iOS에서는 ActivityKit 기반 Live Activity를 사용해 잠금화면과 Dynamic Island에 러닝 상태를 표시했습니다.

이 부분은 Flutter 앱이지만 실제 모바일 환경에 필요한 기능을 Android와 iOS 네이티브 기능으로 보완한 사례입니다.

## 13. AI Running Analysis: AI 리포트 생성 흐름

### 핵심 메시지

- AI 분석은 현재 러닝과 유사한 과거 기록을 찾은 뒤, 그 결과를 context로 전달해 리포트를 생성한다.
- 유사도는 embedding score, numeric score, spatial score를 조합한다.
- Source Feature Retrieval → Similarity Score → Generation → Persistence 흐름으로 설명한다.
- 리포트는 요약, 개선점, 다음 목표, 코칭 문구를 생성하고 run_ai_reports에 저장되어 결과/분석 화면에 표시된다.

### 발표 대본

다음은 AI 리포트 생성 흐름입니다.

AI 분석은 현재 러닝 하나만 보고 바로 문장을 생성하는 방식이 아닙니다. 먼저 현재 러닝과 유사한 과거 기록을 검색합니다.

유사도는 embedding score, numeric score, spatial score를 조합해 계산했습니다. 즉, 기록의 의미적 특징, 거리나 페이스 같은 수치 정보, 경로의 공간적 유사도를 함께 고려합니다.

이렇게 검색된 기록을 context로 전달하고, AI는 이를 바탕으로 현재 러닝의 요약, 개선점, 다음 목표, 코칭 문구를 생성합니다. 생성된 리포트는 저장된 뒤 결과 화면이나 분석 화면에서 확인할 수 있습니다.

## 14. RAG System Design: RAG 확장 설계

### 핵심 메시지

- 현재 구현 범위는 사용자 러닝 데이터 기반 retrieval이다.
- 문서 기반 RAG와 자연어 기록 질의는 향후 확장 범위로 분리되어 있다.
- 현재는 runs, run_splits, territories, point_history 같은 구조화 데이터를 SQL/RPC로 조회하고, 유사 기록을 AI context로 전달한다.
- 향후에는 러닝 코칭 문서, 포인트/영토 규칙, 사용자 기록 질의를 함께 검색해 LLM 답변을 만들 수 있다.

### 발표 대본

다음은 RAG 확장 설계입니다.

현재 구현 범위는 사용자 러닝 데이터 기반 retrieval입니다. 즉, 사용자의 과거 러닝 기록을 검색하고, 그 결과를 AI 리포트 생성의 근거로 사용하는 구조입니다.

다만 문서 기반 RAG와 자연어 기록 질의는 별도 확장 범위로 설계했습니다. 예를 들어 러닝 코칭 문서, 포인트 규칙, 영토 규칙 같은 문서를 chunk와 embedding으로 검색할 수 있습니다.

또 사용자가 "내 최근 기록을 보면 어떤 점을 개선해야 하나"처럼 자연어로 질문했을 때, 허용된 RPC를 통해 사용자 기록을 조회하고, 그 결과를 grounded context로 전달하는 구조로 확장할 수 있습니다.

## 17. Key Challenges: 구현 중 처리한 주요 문제

### 핵심 메시지

- 이 장은 프로젝트에서 실제로 어려웠던 부분을 설명하는 핵심 챕터다.
- 주요 문제는 GPS 오차 필터링, 러닝 상태 보정, 영토 geometry 처리, 백그라운드 실행, AI 분석 안정화, 데이터 정합성이다.
- 발표에서는 문제가 있었다는 사실보다, 문제를 어떻게 계층별로 나누어 확인하고 수정했는지를 강조한다.
- 특히 대학 프로젝트 발표에서는 "시행착오와 해결 과정"이 구현 결과만큼 중요하다.

### 발표 대본

구현 중 처리한 주요 문제도 있었습니다.

첫 번째는 GPS 오차 필터링입니다. 부정확한 위치나 비정상적으로 빠른 이동이 기록에 반영되면 거리와 페이스가 왜곡되기 때문에, 위치 정확도와 이동 속도를 기준으로 필터링했습니다.

두 번째는 러닝 상태 보정입니다. 일시정지 시간을 제외하고, 재개 후 갑자기 먼 위치가 들어오는 경우를 별도 segment로 처리해 거리 왜곡을 줄였습니다.

세 번째는 영토 geometry 처리입니다. GPS 경로를 PostGIS geometry로 변환하고, 사용자 영토를 생성, 병합, 차감하는 서버 로직을 구성했습니다.

네 번째는 백그라운드 실행입니다. Flutter 앱 외부에서 Android foreground service와 iOS Live Activity를 연동해 실제 러닝 환경을 보조했습니다.

다섯 번째는 AI 분석 안정화입니다. 유사도 계산과 structured output schema 오류를 수정하고, 실제 기기에서 리포트 생성이 가능한지 검증했습니다.

마지막으로 데이터 정합성 문제도 처리했습니다. 포인트 집계가 누락되는 문제를 migration과 backfill로 수정하고 테스트로 확인했습니다.
